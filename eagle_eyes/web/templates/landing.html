An RPA bot failed at 3am. Eagle Eyes says why.

A failure leaves three things behind on the machine that ran it: an execution log, a screenshot of whatever was on screen, and the source of the bot itself. A developer opens all three, reads across them, and works out what happened. Eagle Eyes does that correlation and hands back a root cause, a suggested fix, and an honest confidence in both.

How it works

1 · Correlate, don't summarise

A log says ElementClickInterceptedException. The screenshot shows a session-timeout banner covering the button. The source shows a click with no wait and no retry. None of those three is the answer; together they are. Each input is sanitized before it goes anywhere — credentials, tokens, account numbers and personal data are removed first, and the sanitizer is tested against a corpus seeded with exactly those.

2 · Deduplicate, because failures repeat

Failures are fingerprinted on what actually distinguishes them — the innermost exception in a ---> chain, the top stack frames, the message with timeouts, session ids, versions and addresses normalised out. When a spike produces two hundred failures, it produces one fingerprint, and one analysis answers all of them.

This is not a detail. Before the Selenium version trailer was normalised out, a Chrome auto-update silently fragmented every fingerprint and tripled the bill with nothing in the logs to show for it.

3 · Refuse to guess

Two screenshots sit within seconds of the failure: it attaches neither and says why. The source was edited after the failure: confidence is capped and the report says the code may not be what ran. The model returns something unparseable: the report says the analysis did not complete, at zero confidence. A diagnosis that sounds right and is not is worse than no diagnosis, because someone acts on it.

4 · Access is enforced where the data is

Registration grants nothing: a new account can sign in and see nothing until an administrator approves it with a role. An administrator sees everything, a manager sees the service lines in their scope, and a developer sees failures on the bots they own — enforced in the query that selects the rows, not in a check on a route somebody can forget to add to the next page.

What this instance is

A demonstration, on synthetic data, making real model calls.

The bots, logs, screenshots and source here are fabricated. The analysis is not simulated — it is the same engine, the same prompts and the same provider a deployment would use. The product's security argument is that client data never leaves the estate that captured it, which is exactly why there is none of it here. What a real deployment must change before it sees real data is written down separately, in docs/PRODUCTION_MIGRATION.md.
